# Vibe Compiler (vbc) — Design Review

## Executive summary

The spec is a strong statement of *philosophy* — the border discipline (§2) is genuinely good and the worked examples (§7) make it concrete — but it is not yet executable as a deterministic skill. Because "the compiler" is an LLM following these instructions, every place the spec leaves a choice unresolved becomes cross-run divergence, which is the exact failure mode the tool exists to eliminate. The repo today contains *only* the spec (no SKILL.md, no IR/report/project.md templates — all deferred in §12), so two competent agents handed the same `vbc/` and the same command will mutate the working tree differently. The most damaging gaps are not edge cases: a directory containing one blocking file (§4 vs §6 give opposite outcomes), the identity key the whole cache/drift model is built on (`symbol-path`, §5/§6, defined only for one method shape), and the two most common entry points — greenfield "I'm writing pseudo for code that doesn't exist yet" and "I ran compile before validate" — have no defined path at all. These must be closed before implementation, because the IR/report formats deferred to §12 cannot be designed without first fixing the semantics below.

## What actually happens when you run this (distilled from execution traces)

Running the four canonical scenarios as an agent whose only instructions are this doc:

- **Greenfield (`/vbc-compile vbc/` on a new project, §7.1 pseudo, no code, no `.vbc/project.md`).** §4 phase 3 assumes a *validated IR* exists; none does. The agent must improvise whether to refuse / silently validate / compile-from-scratch. Even if it proceeds, §3/§4.2's only verb is "link"/"reconcile" against existing code — there is no "create from nothing" mode, no rule for output path (`Cache.cs`? `src/Cache.cs`?), and *the target language itself is unknown* because §1 forbids inferring language from pseudo syntax and there's no project.md. "I don't know the target language" is an axis-2 irreversible choice but there is no BLOCK for it.
- **Validate mismatch (§7.3, code drops MRU, pseudo says "drop LRU").** The BLOCK report prose is fully specified and good. But the BLOCK *only fires because the agent chose to read a free-text comment as a normative claim* — §1 says pseudo "ranges freely from natural language" and nothing marks which comments are load-bearing. A different agent ignores the comment, labels `Evict` OK (as the §7.1 table does for bare `Evict`), and validate gives a **false PASS on code that does the opposite of intent**. Worse, the §7.3(b) "intended change → acknowledge and use /vbc-compile" path has **no acknowledgment mechanism**: re-running compile re-triggers the same BLOCK because the pseudo still can't be linked to the old code — a deadlock the agent can only escape by inventing an artifact the spec doesn't authorize.
- **Directory + one block (5 files, 4 clean, `trending.vibe` blocks).** §4 says "no code anywhere"; §6 says incremental make. Opposite filesystem outcomes, no precedence rule.
- **Drift / rename (teammate renames `Evict`→`EvictLru` and edits the body).** The stored symbol-path `LruCache.Evict` now dangles; §6 claims linkage is "robust" but rename is exactly what symbol-path does not survive. There is no defined branch for "linked symbol gone," so the agent either regenerates a duplicate `Evict` (split-brain with the teammate's `EvictLru`) or fuzzy-relinks and silently clobbers the hand-edited body under an undefined "significant gap" threshold.

**Cross-cutting:** in all four, the agent must invent the IR row format, report layout, and drift threshold — all explicitly deferred to a §12 implementation plan that does not exist in the repo. The audit trail the border discipline depends on is itself unspecified.

## Confirmed issues, grouped by theme

### Theme A — Contradictions between two literal spec sentences (highest priority: same input, opposite observable output)

#### A1. Global hard-halt (§4) contradicts incremental make-style compile (§6) on a directory — **CRITICAL**

§4 says unconditionally: "If **any** BLOCK exists, no code is produced **anywhere** until every BLOCK is resolved." §6 frames directory compile as incremental and file-granular, "like an incremental `make`," reprocessing "a changed file and its dependents" and leaving the rest alone. For a directory of one blocking file plus several independent clean files, these prescribe opposite filesystem mutations, and no precedence rule exists.

- **Failure scenario.** `vbc/ = {cache.vibe (clean), auth.vibe (clean), trending.vibe (surprise=??? → BLOCK per §7.2)}`. `/vbc-compile vbc/`. Agent A applies §4 literally → writes nothing, all three held hostage by an unrelated feature. Agent B applies §6's make model → patches cache + auth, reports trending blocked. Same repo, same command, opposite working-tree mutations. A real `make` *does* build targets whose own inputs are clean, so whichever rule wins, the other sentence is dead/false text.
- **Decision / recommended resolution.** Pick one rule and state it for *both* validate and compile. Recommended: scope the hard-halt to the **connected dependency unit being processed** (the §6 "changed file and its dependents" set) — independent clean files still produce code; only the blocked unit halts. Then state per-file atomicity (a file's symbol patches apply all-or-nothing) and require the report to list compiled-vs-blocked files. Add a worked directory example.

#### A2. §6 claims symbol-path linkage is "robust"; rename breaks it, and "linked symbol gone" has no branch — **MAJOR**

§6's robustness claim conflates reformat/move-elsewhere (survives) with rename (does **not** — the symbol-path *is* the identity, and rename changes it). §10's YAGNI list excludes only character-span linkage and non-git projects, not rename. There is no defined behavior for "the linked symbol no longer exists at its path."

- **Failure scenario.** Teammate renames `Evict`→`EvictLru` at commit X+1. `/vbc-compile vbc/cache.vibe`. Read-only git on `LruCache.Evict` finds nothing at that path; drift detection itself has no result. Agent A treats it as "deleted" and regenerates a fresh `Evict` beside `EvictLru` (split-brain duplicate); Agent B silently relinks to the closest match and may patch the wrong symbol. Routine refactor → cross-run divergence.
- **Recommended resolution.** State explicitly that rename breaks symbol-path linkage. Define recovery: similarity-match (signature + body) within the linked file, propose the rename as a re-link **for user confirmation**, and treat an unconfirmed re-link as a **BLOCK** rather than guessing. Specify the similarity threshold or fold it into the §12 "significant gap" knob. (This is the same undefined threshold that, in the body-edit sub-case, decides whether compile silently clobbers a teammate's hand edit — an axis-2 "costly/irreversible" event that §6 currently only *notifies* on rather than halting.)

### Theme B — The identity key the whole model rests on is underspecified

#### B1. `symbol-path` is the linchpin of linkage/drift but is concretized only for a method-on-a-type — **CRITICAL**

The entire linkage *and* drift model keys on `pseudo element → (file, symbol-path)`, and the only example anywhere is `LruCache.Evict` (§5). There is no grammar or resolution rule for: free/module-level functions, the §7.2 module-scope driver loop (`for window in tumbling_windows(...)`), overload sets (two `Get`-style cases), lambdas/closures, or one-to-many linkage — even though §7.1 maps a single table row ("MoveToFront, InsertAtFront, Evict, map.Find") to four symbols at once. §12 defers the "IR Markdown schema" (formatting), but symbol-path *identity* is the §6 build-cache and drift-detection key, not formatting.

- **Failure scenario.** Validate `trending.vibe` (§7.2). Agent A keys the module driver loop as `trending.<module>` and `surprise`/`normalize` as children of `find_trending`; Agent B keys the loop as `trending.__main__` and `surprise` as a top-level free function `trending.surprise`. Next `/vbc-compile`: the committed IR keys no longer match the freshly derived keys; §6 drift comparison of `(file, symbol-path)` keys disagrees, so it either flags everything stale (defeating the incremental cache, reprocessing the whole file) or fails to locate the symbol to patch. The audit trail forks between authors.
- **Recommended resolution.** Specify, per supported language, a canonical symbol-path grammar (separators; how module scope and module-level statements are named; overload disambiguation by arity/signature; lambda/closure anchoring to the enclosing named symbol) and an explicit one-to-many / many-to-one linkage representation. Provide a worked symbol-path table for **both** §7.1 and §7.2 covering every referenced symbol, not just one method.

### Theme C — The two most common entry points have no defined path

#### C1. Greenfield (no existing code) is undefined; validate is reality-relative and new-code language/layout are improvised — **MAJOR**

Every definition of validate is brownfield: §3 "Can this pseudo faithfully describe the *existing* code?"; §4 "links the pseudo to the actual implementation"; §7.3 "does this pseudo describe what the code *currently is*." For brand-new pseudo, every linkage target is null. §7.3's only BLOCK example — "pseudo cannot be linked to current code" — read literally, fires on *every* greenfield symbol, making validate unusable for new code; unless missing symbols are silently OK, which then hides a typo'd symbol name in brownfield. The spec gives no rule to distinguish "intentionally net-new symbol" from "broken link." §5 says project.md declares target language/layout, but greenfield users typically haven't written it, and §1 forbids inferring language from pseudo syntax.

- **Failure scenario.** New module: `trending.vibe` for code that has no implementation, no project.md, no IR; `/vbc-validate`. Per §4 every link fails. Agent A → every missing symbol is a §7.3 BLOCK → validate always hard-halts, tool can't bootstrap. Agent B → missing symbols silently fine → a mistyped symbol name in real brownfield now passes silently. After resolving, compile must invent target language (C# vs guess), file path (`Cache.cs` vs `src/...`), namespace — an irreversible axis-2 choice with no "language unknown" BLOCK.
- **Recommended resolution.** Add an explicit greenfield path: a linkage to a symbol absent from the *entire* codebase is **not** a §7.3 BLOCK but a recorded "to-be-created" linkage (status `NEW`), distinct from "symbol present but behavior diverges" (§7.3 BLOCK). Compile generates net-new code for `NEW` linkages at layout-derived paths and surgically patches `EXISTING` ones, recording invented file/symbol/language choices as ASSUME entries. Make a missing/ambiguous target language (no project.md) a hard **BLOCK** — the one place the tool *should* refuse to guess.

#### C2. Compile's precondition (a validated IR baseline) is undetectable from IR state — **MAJOR**

§4 phase 3 is written assuming compile's input is "the *validated* pseudo," i.e. a verified IR baseline exists. §9 mandates validate-first but §4 never says what compile does when no IR entry exists, or when the entry came from a validate run that itself hard-halted on a BLOCK (incomplete IR). The IR (§5) records linkage, labels, validated-at commit, content hash — but there is no per-file status distinguishing UNVALIDATED / VALIDATED-CLEAN / VALIDATED-BLOCKED / EDITED-SINCE-VALIDATION. From "no IR entry" or "hash differs" alone, compile can't tell these apart.

- **Failure scenario.** New user writes `cache.vibe`, runs `/vbc-compile` (skips validate). No baseline. Agent A refuses; Agent B silently runs validate; Agent C treats it as greenfield. Worse: a validate that *hard-halted* leaves a partial IR; compile sees "an IR entry exists" and surgically patches against symbols whose linkage was never completed — applying an intended-change diff onto code it never confirmed matched the pre-edit pseudo.
- **Recommended resolution.** Make compile's precondition explicit and checkable: require, for every symbol being patched, an IR entry whose validated-at commit is an ancestor of HEAD; if missing / stale / from a blocked validate, compile **STOPS** and instructs the user to validate first. Record a per-file **status enum** (`UNVALIDATED` / `VALIDATED_CLEAN` / `VALIDATED_BLOCKED` / `EDITED_SINCE_VALIDATION`) in the IR so compile branches deterministically instead of inferring intent from a bare hash. (This enum is also the natural home for the §7.3(b) "intended change" acknowledgment that the validate-mismatch trace showed has no mechanism — see Theme D.)

### Theme D — Silent paths that defeat the audit trail (border discipline turned against itself)

#### D1. Premise/Policy promotion has no scope syntax or staleness re-check; a stale or mis-scoped premise silently green-lights wrong code — **MAJOR**

A Premise promotes a would-be BLOCK → OK, and OK is **silent** (§2: only ASSUME is surfaced). The spec gives premises free-text form ("single-threaded unless a construct uses locks"), unlimited untyped scope, and no expiry/re-confirmation when the premise's truth changes. §12 defers policy syntax, but matching a premise to a specific call is the *operative mechanism* of §2 promotion — without a scope grammar the LLM matches by freeform judgment, and nothing re-flags a premise reality has falsified. The IR records *which* premise resolved a call, but recording is not verifying.

- **Failure scenario.** project.md declares "single-threaded unless a construct uses locks." Per §7.1 this promotes the `_evictLock`/unsynchronized-`Get` BLOCK → OK and emits non-thread-safe `Get` with no surfaced note. Months later a worker pool is added; the premise is now false but still on the page. Next compile silently re-applies BLOCK → OK and ships a data race — the exact axis-2 concurrency contract the border exists to catch, now invisible. Separately, two agents disagree on whether "single-threaded" covers an async/await continuation with no explicit lock: one promotes, one hard-halts, same input.
- **Recommended resolution.** (1) Require BLOCK→OK premise promotions to **still emit a one-line surfaced note** ("resolved OK under premise X") so promotion is auditable at code-review time, not only in the IR. (2) Define premise scope syntax (which files/symbols/constructs a premise governs) so matching is deterministic. (3) Add a re-validation trigger: when validate detects code contradicting a premise (locks/threads appear), flag the premise as possibly-stale BLOCK instead of relying on it.

#### D2. Compile has no dry-run / review-before-write gate and assumes a clean, non-empty git history — **MAJOR**

§4 says compile "applies changes to the real implementation" and §5 says the IR is committed and records the git commit each linkage was validated against — the tool mutates source and writes git artifacts. The only specified guard is the BLOCK hard-halt, which fires on *detected* criticality, not on ordinary confidently-wrong OK/ASSUME generation. No diff preview / confirmation gate is specified between generation and writing. Separately §6 leans on git operations that fail in states §10 never excludes: no initial commit (nothing for the "validated-at commit" to anchor), detached HEAD, untracked `vbc/`, or a dirty tree mixing user and compiler edits.

- **Failure scenario.** Fresh repo, nothing committed, no project.md. `/vbc-compile vbc/`. The LLM rationalizes `surprise` (§7.2, which should BLOCK) as "the one reasonable z-score" → OK, writes plausible-but-wrong code straight into real source. There is no commit for the IR's validated-at field to reference, so that field is empty/invalid, and the change lands with no diff preview or confirmation. Because OK is silent, the wrong implementation is never surfaced for review.
- **Recommended resolution.** Require an explicit **review-before-write gate** for compile (emit proposed diff + border report; write only on confirmation) and make committing opt-in, not implicit. Enumerate git preconditions: refuse/warn when there is no baseline commit to anchor linkage; never fold compiler edits into a pre-existing dirty tree without isolation. (The no-initial-commit and missing-write-gate cases are concrete; detached-HEAD/dirty-tree are weaker and can be handled as warnings.)

## Strengths worth preserving

- **The border axes (§2)** are the real asset: defining BLOCK by *axes* (divergent alternatives / costly-irreversible / viability-threatening) rather than by category is what keeps the discipline robust to novel cases. Keep this front and center.
- **The decomposition rule (§2)** — "add the guard = ASSUME, what the guard does = OK or BLOCK" — is exactly the kind of guidance that reduces agent variance. More rules in this style would directly mitigate the symbol-path and comment-interpretation ambiguities.
- **The §7.3 validate-mismatch report prose** is fully specified and is a model for how every BLOCK report should read. The "validate cannot tell a mistaken description from an intended change, so it hard-halts and makes the user choose" framing is the correct keystone — it just needs the missing acknowledgment mechanism (Theme C2/D) to be completable.
- **Symbol-level (not character-span) linkage (§6/§10)** is the right call for surviving reformatting; it only needs the rename branch and the path grammar to deliver on its robustness claim.
- **Two-phase validate-then-compile with a read-only validate (§4/§9)** is a sound spine and a good safety posture; the gaps are in the unstated preconditions between phases, not the shape.
